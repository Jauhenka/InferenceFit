# InferenceFit 0.1.0 Release Design

## Purpose

Prepare the existing InferenceFit implementation for its first public open-source release without adding product features or publishing a production package. The release candidate must be reproducible, installable from built artifacts, understandable to a new developer, safe to publish, and backed by explicit CI and release-owner instructions.

The task ends with either `READY_FOR_0.1.0` or `BLOCKED_FOR_0.1.0`. Production publication and pushing the `v0.1.0` tag remain deliberate human actions.

## Scope and constraints

The work is limited to packaging metadata, public documentation, build and installation verification, repository hygiene, CI, release workflows, and release evidence. Existing benchmark, provider, optimization, artifact, CLI, API, and daemon behavior must not be redesigned.

The release process must:

- preserve the distribution name `inferencefit` and version `0.1.0`;
- support `pip install inferencefit`, `inferencefit --help`, and `from inferencefit import benchmark`;
- use only deterministic fixture workloads in ordinary CI and installed-package smoke tests;
- never require provider credentials or make paid inference calls in ordinary CI;
- use PyPI Trusted Publishing through OIDC rather than long-lived upload tokens;
- keep TestPyPI and production PyPI publication paths separate;
- never publish to production PyPI or push a release tag during this task;
- preserve existing user changes in `README.md`, `LICENSE`, `AGENTS.md`, and `.github/` unless a release requirement calls for a compatible edit;
- avoid unrelated dependency modernization and all E1 product work.

## Repository and metadata design

`pyproject.toml` remains the packaging authority. Hatchling remains the build backend. The package's `src/inferencefit/__init__.py` `__version__` value becomes the single maintained version value by configuring Hatch to read it dynamically. This keeps `import inferencefit; inferencefit.__version__` functional in an installed wheel without relying on Git metadata.

The project metadata will include the Apache-2.0 license, README long description, Python requirement, useful classifiers and keywords, and URLs derived from the configured GitHub remote. No personal author or maintainer information will be invented. Runtime and development dependencies remain separate; Twine is added only to development tooling.

The sdist policy will retain files useful to source consumers while excluding local state, build output, credentials, internal agent instructions, and implementation-planning material. The wheel will continue to contain only the importable package and distribution metadata.

## Documentation design

The README will be revised as a first-contact document. Its opening sections will explain the workload-specific evaluation model, installation from PyPI, a deterministic offline quick start, a real-provider example, CLI and Python entry points, `EvaluationSpec`, generated artifacts, provider scope, local daemon use, limitations, detailed-document links, and Apache-2.0 licensing. It will not claim hosted or roadmap capabilities as available.

Release-specific documents will be added:

- `CHANGELOG.md` records the implemented 0.1.0 capabilities.
- `docs/release-0.1.0.md` is the live checklist and final verification record.
- `docs/releasing.md` gives exact GitHub, TestPyPI, and PyPI Trusted Publisher setup and human release steps.
- `docs/releases/0.1.0.md` is a concise GitHub Release body draft.

The existing architecture, contracts, and E0.5 validation report remain detailed supporting references.

## CI and release automation

Ordinary CI will use a compact matrix:

- Ubuntu tests on Python 3.11, 3.12, and 3.13;
- representative Windows tests on Python 3.13;
- a dedicated packaging job that builds wheel and sdist, runs Twine checks, inspects distributions, and runs the installed-distribution smoke test.

CI must not read provider secrets or run live provider specifications.

Production release automation lives in `.github/workflows/release.yml`. A `v*` tag starts a build-and-verify job, uploads the exact distributions as a workflow artifact, and then a separate publish job downloads that artifact. Only the publish job receives `id-token: write`, uses GitHub environment `pypi`, and invokes the official PyPA publishing action. It never rebuilds distributions.

TestPyPI automation lives in `.github/workflows/testpypi.yml` and is invoked explicitly through `workflow_dispatch`. It follows the same immutable-artifact pattern, publishes through environment `testpypi`, and targets TestPyPI. Account-side Trusted Publisher and GitHub environment configuration remain documented human setup steps.

## Installed-distribution smoke test

A cross-platform Python smoke script will validate the built distribution rather than the editable working tree. CI and local release verification will:

1. create a clean temporary virtual environment;
2. install the built wheel, and separately the sdist when feasible;
3. run from outside the repository source directory;
4. verify `inferencefit.__version__ == "0.1.0"`;
5. verify the installed `inferencefit` entry point and `--help` output;
6. create a temporary synthetic dataset, fixtures, and EvaluationSpec;
7. execute a deterministic benchmark and verify its result and artifacts.

Dependency download may be required while installing the distribution, but the smoke benchmark itself must be offline and require no credentials.

## Privacy and package-content audit

The release audit will inspect both committed content and the exact final wheel and sdist. It will search for secret-like strings, bearer tokens, provider keys, real-looking contact information, private URLs or identifiers, `.env` files, `.inferencefit` runs, caches, virtual environments, stale distributions, and production-derived source artifacts.

Synthetic examples will not be removed merely because their values resemble realistic data. The E0.5 report's sanitization statement will be checked against the actual public datasets. Any ambiguous match will be reviewed manually and recorded in the release checklist.

Archive inspection will verify that required Python modules, README metadata, and license data are present, and that local or internal artifacts are absent. Final wheel and sdist filenames and byte sizes will be recorded.

## Verification strategy

The final release-candidate pass starts by removing stale `dist/` and `build/` directories, then runs:

```text
pytest
ruff check .
ruff format --check .
python -m build
twine check dist/*
```

It also runs both public fixture workloads, archive inspection, privacy and secret scans, clean wheel installation, clean sdist installation when feasible, version import, CLI help, and the installed offline benchmark.

Python 3.11, 3.12, and 3.13 are the declared targets. Local interpreters or isolated tooling will be used where available; the GitHub Actions matrix is the authoritative cross-platform verification before the human release. Versions not actually executed will be reported as unverified rather than silently claimed.

The distribution name will be checked against both PyPI and TestPyPI immediately before the readiness decision. A legitimate name conflict is a release blocker.

## Failure handling and readiness decision

Release verification fails closed. A failing test, lint or format check, build, Twine check, installed import, installed CLI, installed fixture benchmark, package-content audit, privacy audit, license check, package-name check, or required workflow design produces `BLOCKED_FOR_0.1.0` until corrected.

Unavailable account-side Trusted Publisher configuration is documented as a required human gate. It blocks actual publication but does not invalidate the code-level release candidate when the workflows and instructions are correct. TestPyPI will be exercised only if its Trusted Publisher is already configured and can be invoked intentionally; otherwise no upload is attempted.

Non-correctness warnings, such as upstream deprecations, will be recorded without weakening tests or expanding scope.

## Human release boundary

No production package or tag is created by this task. When code-level preparation is complete, the final report will provide commands matching the actual branch and workflow files. The human release owner will review and commit the release changes, push them, configure and approve the `testpypi` and `pypi` environments and Trusted Publishers, verify CI and TestPyPI, then deliberately create and push the annotated `v0.1.0` tag.
