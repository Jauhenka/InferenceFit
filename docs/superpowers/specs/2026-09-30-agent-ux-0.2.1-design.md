# Agent UX and Workload Presets 0.2.1 Design

## Intent and success criteria

InferenceFit 0.2.1 makes the existing benchmark workflow easier to start for both humans and
coding agents. A user should be able to discover a small set of workload-shaped starters,
materialize a valid local project, replace the samples with representative cases, configure the
providers already available to them, and run the normal InferenceFit benchmark path without
reconstructing `EvaluationSpec` YAML from memory. A portable Agent Skill teaches compatible
agents the same cost-conscious workflow.

This is a developer-experience and agent-UX release. It does not change the benchmark engine,
serialized schema, provider abstraction, optimizer, artifact format, or HTTP API. Success means:

- exactly `coding`, `document-processing`, and `structured-extraction` are discoverable;
- `inferencefit init --preset <id> <destination>` creates valid, inspectable, offline-runnable
  starter files without overwriting existing paths;
- the generated project runs through `load_evaluation_spec()`, `load_jsonl_dataset()`, and the
  existing public `benchmark()` orchestration;
- a concise vendor-neutral `inferencefit/SKILL.md` workflow ships in wheels and sdists and can be
  located after installation;
- installed-distribution smoke tests prove the CLI, presets, and skill resources work outside the
  source tree; and
- the 0.2.0 provider, benchmark, resume, artifact, CLI, API, packaging, and release behavior stays
  green.

The design is based on `codex/multi-provider-0.2.0` at commit `a44b2ca`. The current checkout was
on `main` while this document was authored, so repository evidence was read from that branch with
`git show` rather than by switching a dirty working tree.

## Repository fit

The 0.2.0 CLI is a small Typer application in `src/inferencefit/cli/__init__.py`. Its entry points
are thin wrappers around shared Python functions. `EvaluationSpec` requires a JSONL dataset and at
least one candidate. The fixture provider can execute a complete benchmark offline when the spec
points its `parameters.fixture_path` at packaged sample responses. Validators are declarative and
global to the dataset; the available types are exact, regex, enum, JSON Schema, numeric, contains,
and trusted local Python callables. There is no built-in semantic-judge validator.

Provider construction is centralized in `src/inferencefit/providers/registry.py`, while credential
resolution reads opaque references and documented environment-variable fallbacks without writing
values to artifacts. The release machinery already builds with Hatch, audits wheel and sdist
members and secrets, installs each artifact into an isolated environment, and exercises the
installed CLI. Package version has one maintained source in `src/inferencefit/__init__.py`.

These boundaries favor package resources and a thin CLI over a second execution path, dynamic
plugins, or a new benchmark contract.

## Scope and non-goals

Version 0.2.1 adds:

1. a fixed registry containing exactly three built-in workload presets;
2. static canonical project templates for those presets;
3. `inferencefit presets` and `inferencefit init --preset ... DESTINATION`;
4. a portable Agent Skills-compatible `inferencefit` skill with three focused references;
5. `inferencefit skill path` so an installed package can reveal the canonical skill directory;
6. packaging, installed-distribution, documentation, and release updates for 0.2.1.

It does not add providers, provider rankings, provider/model catalogs, LCAI, a custom-provider
framework, Cloud, accounts, authentication, billing, hosted keys, non-Python SDKs, a web UI, a
plugin marketplace, autonomous background benchmarking, dataset downloading, a large preset
catalog, a TUI, or a benchmark-engine redesign. It also does not add a semantic judge, execute
untrusted generated code, or promise that a generated toy dataset is decision-quality.

## Architecture decision

Use a hybrid of a small typed registry and static package templates.

`src/inferencefit/presets/__init__.py` owns an immutable `PresetDefinition` with three fields:
`identifier`, `description`, and `template_name`. It exposes deterministic `list_presets()` and
`get_preset(identifier)` functions. The built-ins are a tuple in the required display order;
there is no registration API, entry-point loading, or plugin mechanism.

`src/inferencefit/presets/project.py` owns project materialization. It resolves a registry entry,
copies the matching trusted resource directory, validates the copied `eval.yaml` and
`cases.jsonl` with the real loaders, and returns the created paths. It never calls the benchmark
engine and never interprets a workload differently after initialization.

Templates live under the importable package:

```text
src/inferencefit/presets/templates/
├── coding/
│   ├── eval.yaml
│   ├── cases.jsonl
│   ├── fixtures/sample.jsonl
│   └── README.md
├── document-processing/
│   └── ...same four files...
└── structured-extraction/
    └── ...same four files...
```

Static files are preferable here because users are expected to read and edit the generated YAML,
JSONL, and Markdown. They keep the canonical output reviewable, diffable, and easy to audit.
Constructing large nested dictionaries in Python would make copy changes harder to review without
providing meaningful schema safety beyond the real parser tests. A fully data-driven template or
plugin engine would be unjustified for three fixed starters.

Alternative designs rejected:

- **Programmatic contract serialization:** type-aware, but it mixes prose and sample data into
  Python, loses purposeful comments, and still needs golden integration tests.
- **Repository-root templates copied by path:** convenient from a checkout, but unavailable after
  a normal wheel install unless duplicated or specially mapped.
- **A generic preset/plugin API:** more extensible, but creates lifecycle and compatibility
  promises before external presets are a demonstrated need.

## Preset project contract

Every generated project contains the same four resource roles:

- `eval.yaml` is a valid schema `0.1` `EvaluationSpec` that points to `cases.jsonl` and one
  deterministic `fixture` candidate named `sample-baseline`.
- `cases.jsonl` contains two small synthetic cases demonstrating the preset's expected structure.
- `fixtures/sample.jsonl` contains matching responses, token counts, and small deterministic
  latencies so `inferencefit benchmark eval.yaml` runs offline.
- `README.md` explains the preset assumption, the validator choices, where to replace cases and
  candidates, the run command, and why sample success is not evidence for model selection.

The fixture candidate is a plumbing check, not a model recommendation. Its model name is explicitly
synthetic and it contains no credential or endpoint. Each README begins with the warning:

> Replace the sample cases with representative production examples before using the benchmark for
> model-selection decisions.

The starter uses one repetition, modest concurrency, bounded timeout/retry settings, and the
`max_quality` objective so the offline candidate remains rankable without invented provider
pricing. Users or agents add real candidate pricing snapshots only when configuring real
providers. No preset embeds a live model ID, a provider preference, a hard-coded ranking, or an API
key placeholder that could be mistaken for a credential.

Generated projects are snapshots. A 0.2.1 project records schema version `0.1` and continues to be
handled by the existing compatibility policy. Future releases update their bundled templates and
tests together; they do not silently rewrite an initialized project. If a future schema becomes
incompatible, that release must provide normal schema migration or a new preset template version,
not special execution semantics.

### Safe materialization

Initialization is non-interactive and fail-closed:

- the destination parent must already exist and be a directory;
- any existing destination entry, including a file, directory, or dangling symlink, is a conflict;
- 0.2.1 has no `--force` or overwrite mode;
- the command creates only the requested destination and its trusted template contents;
- on a copy or validation failure, files created by this invocation are removed and the original
  error is reported without a traceback for expected user errors; and
- copied files are validated before success is printed.

This favors data safety over convenience. Deep parent creation and overwrite semantics can be
considered only after real usage demonstrates a need.

## The three presets

### `coding`

The sample workload is a small code-transformation task whose response is JSON with a required
`code` string. JSON Schema proves parseability and shape; an exact validator compares `/code` with
`expected.code`. This deliberately demonstrates the simplest deterministic expected-output path.

The README explains that exact text is often too brittle for real code generation. When a project
already has unit tests, an agent should prefer a trusted local Python validator that calls a narrow
test harness or otherwise reuses deterministic tests. It must not execute untrusted model output
merely because the preset is named `coding`. The preset does not become an autonomous coding
benchmark framework. Real candidate configuration should keep output limits small during the
exploratory run and compare quality, latency, reliability, and known cost.

### `document-processing`

The generated example is intentionally one concrete, deterministic document-classification
shape: a short synthetic document maps to a JSON `label`. JSON Schema checks shape and an exact
validator checks the label. This gives the broad preset a runnable baseline without pretending
that classification, question answering, summarization, synthesis, and long-input processing use
one quality metric.

The README describes how to replace the sample with the user's actual document task. Exact or
enum checks suit classification and extractive QA; custom deterministic checks may suit known
facts; summarization and synthesis require a task-specific rubric and, only when genuinely needed,
a trusted semantic evaluation path supplied by the project. InferenceFit 0.2.1 does not claim a
built-in semantic judge. Long-input cases should start with a few representative documents because
input length can dominate cost.

### `structured-extraction`

The sample asks for one JSON object with required typed fields. JSON Schema proves parsing,
required fields, field types, and rejection of unexpected fields. A root exact validator
(`target: ""`, `reference: ""`) checks the complete parsed object against expected data. The
sample uses two synthetic records with no real personal or business data.

The README recommends low temperature where the chosen provider/model supports it, bounded output,
and field-level exact/numeric validators when whole-object equality is too strict. The single
preset is reusable for invoices, forms, resumes, contracts, metadata, and structured
transformations; 0.2.1 does not split those into separate domain presets.

## CLI design

### Preset discovery

`inferencefit presets` prints one deterministic line per registry entry in registry order:

```text
coding: Code generation and transformation with deterministic checks.
document-processing: Document classification and adaptable document-quality evaluation.
structured-extraction: Schema-checked JSON extraction with exact expected fields.
```

The identifiers and line grammar are stable public CLI behavior for 0.2.1. Descriptions may be
edited only with corresponding tests and release review. Output contains no terminal-dependent
table decoration and is readable by both humans and agents.

`--json` is deferred. Three fixed `identifier: description` records do not justify a second output
contract, and the rest of the CLI does not yet offer a coordinated machine-readable mode. A future
release should add structured output consistently across discovery, validation, and benchmark
commands rather than start with a one-off flag.

### Project initialization

The command is:

```text
inferencefit init --preset structured-extraction ./eval
```

On success it prints the resolved destination, the four created relative paths, a reminder to
replace sample cases and candidates, and the exact benchmark command. It never prompts. Unknown
presets fail with `Unknown preset '<id>'. Run 'inferencefit presets' to list available presets.`
Destination conflicts and malformed parents identify the path and do not alter it.

Successful commands and help return exit code 0. Usage errors, unknown presets, destination
conflicts, and invalid destination parents return 2. Unexpected filesystem or internal validation
failures return 1 with a concise error on stderr. Existing `validate`, `benchmark`, and `serve`
behavior is unchanged.

### Skill discovery

`inferencefit skill path` prints only the absolute path to the canonical `inferencefit` skill
directory and returns 0. It does not copy, link, register, or mutate an agent configuration. This
single command materially improves installed-package usability while avoiding a universal
installer with vendor-specific locations and permissions.

No `inferencefit providers` command is added. The existing provider registry and README remain the
source of provider configuration. The skill asks which providers the user intends to evaluate,
inspects existing specs, and checks only whether documented credential variable names are present;
it never reads aloud, prints, serializes, or transmits credential values for discovery.

## Portable Agent Skill

The canonical skill lives inside the package so the same source is inspectable in the repository
and guaranteed to travel in wheel and sdist artifacts:

```text
src/inferencefit/skills/inferencefit/
├── SKILL.md
└── references/
    ├── presets.md
    ├── validators.md
    └── interpreting-results.md
```

The directory follows the vendor-neutral Agent Skills specification at
<https://agentskills.io/specification>: `SKILL.md` begins with required `name: inferencefit` and a
description that states both capability and trigger intents. The directory name matches the skill
name. The body stays concise and links only one level deep to focused references. It does not use
vendor-specific tools, filesystem locations, or metadata.

The skill's core workflow is:

1. understand the decision the user needs and the hard acceptance constraints;
2. inspect existing tests, examples, schemas, expected outputs, and representative data;
3. run `inferencefit presets` and initialize the nearest preset, or adapt a custom spec only when
   no preset fits;
4. replace samples with three to five representative cases before drawing conclusions;
5. choose deterministic validators whenever tests, schemas, or expected values support them;
6. configure only providers/models the user can and wants to evaluate, detecting credential
   presence by name without exposing values;
7. summarize the planned live request count, repetitions, token bounds, and known/unknown pricing;
8. run an exploratory benchmark with at most three candidates, five cases, and one repetition by
   default, with bounded output; request confirmation when cost is unknown, input size is large,
   or the run exceeds that exploratory envelope;
9. inspect quality, provider reliability, latency, known cost, constraints, and the Pareto frontier;
10. expand cases, candidates, or repetitions only when the exploratory result justifies it; and
11. explain workload-specific trade-offs rather than claiming a universal best model.

The skill explicitly forbids inventing ground truth when it can be derived from tests, schemas,
examples, or user-provided outputs. It treats a sample fixture run as a setup check only. It warns
that exact and contains validators are not semantic metrics, that local Python validators are
trusted code, and that unknown cost is not zero cost.

The simplest installation workflow is documented, not automated: run `inferencefit skill path`,
then copy or link the returned whole `inferencefit` directory into a skill root supported by the
user's chosen agent. Source users may point at the same directory in the checkout. Agent-specific
destinations remain in the agent's documentation. `inferencefit skill install` is deferred because
portable destination discovery, conflict handling, upgrades, and permissions would turn a small
release into an installer framework.

## Packaging and distribution

Keeping presets and the skill under `src/inferencefit/` lets Hatch include them as package data in
normal wheels while also retaining them in the sdist. Packaging is verified rather than assumed:

- source tests validate the skill frontmatter, directory-name match, references, CLI command
  references, and absence of secret-like content;
- the distribution audit requires every skill/reference file and every preset file in wheel and
  sdist, scans their contents for secrets, and continues to reject internal `docs/superpowers`;
- installed wheel and sdist smoke tests run `presets`, initialize `structured-extraction`, validate
  and benchmark its fixture project, run `skill path`, and read the returned `SKILL.md` outside the
  source tree; and
- release tests pin version `0.2.1`, CI artifact names, changelog, README, and release notes while
  preserving historical 0.1.0 and 0.2.0 documents.

No runtime dependency is added. PyYAML, already required, is sufficient for the focused skill
frontmatter audit; the project does not add `skills-ref` as a runtime or development dependency.

## Error handling and agent-friendly behavior

Expected CLI errors are concise, path-specific, and secret-safe. `presets` and `skill path` do not
read credentials or make network requests. `init` does not run providers. An initialized fixture
benchmark is offline. The skill requires an agent to distinguish configuration validation from a
meaningful evaluation and to state when cost, semantic quality, or ground truth remains unknown.

The CLI prints created locations and next commands explicitly. It does not introduce prompts,
colors required for meaning, progress UI, or terminal cursor control. These properties keep the
commands usable in CI and agent shells without a new machine-readable interface.

## Testing strategy

All new tests are offline.

- **Registry:** exact identifiers/order, non-empty unique descriptions, resource names, and clean
  unknown-preset failure.
- **Initializer:** every preset creates only the expected files; real spec and dataset loaders
  accept them; a fixture benchmark completes; no secret is present; destinations are never
  overwritten; existing files/directories/dangling links and invalid parents fail cleanly; and a
  simulated copy/validation failure leaves no partial destination.
- **CLI:** discovery output, help, initialization, unknown preset, conflicts, stderr, and exit
  codes are stable and non-interactive.
- **Skill:** required frontmatter, name/directory agreement, referenced-file existence, current CLI
  commands, concise size limits, and secret scanning without brittle full-prose assertions.
- **Packaging:** wheel/sdist member requirements, installed resource access, initialized-project
  smoke, and existing archive safety checks.
- **Regression:** the full provider, execution, validator, artifact, resume, API, release, and
  packaging suite remains green.

Final verification uses the established repository commands: full `pytest`, `ruff check .`,
`ruff format --check .`, wheel and sdist build, `twine check`, distribution audit for `0.2.1`,
clean wheel installation smoke, clean sdist installation smoke, installed CLI/preset/skill smoke,
secret scan, and `git diff --check`. A final independent DeepSeek read-only review compares the
diff with this spec; the lead engineer owns all fixes and reruns final verification.

## Explicit answers to the design questions

1. **Where do presets live?** Under `src/inferencefit/presets/templates/<identifier>/` as package
   resources.
2. **Internal representation?** An immutable three-field `PresetDefinition` in a fixed tuple,
   exposed through `list_presets()` and `get_preset()`.
3. **Static or programmatic generation?** Copy static canonical templates, then validate them with
   the real contracts. No second renderer or schema.
4. **Future schema compatibility?** Generated projects are versioned snapshots using schema
   `0.1`; future packages update templates while honoring normal schema compatibility or explicit
   migration rules.
5. **Canonical `SKILL.md` location?** `src/inferencefit/skills/inferencefit/SKILL.md`.
6. **Wheel/sdist inclusion?** Package placement plus mandatory archive-member and installed-smoke
   checks; no duplicate top-level copy.
7. **Simplest exposure to an agent?** `inferencefit skill path`, followed by a documented copy or
   link of the whole directory to the agent's supported skill root.
8. **Any skill CLI?** Include only `skill path`; defer `skill install`.
9. **Machine-readable preset output?** No `--json` in 0.2.1; stable line-oriented text is enough.
10. **Prevent stale model lists?** Templates contain only an offline fixture candidate and the
    skill selects live candidates from the user's current availability; no model recommendations
    are bundled.
11. **Credential reasoning?** Check presence by documented variable name or existing opaque
    `credential_ref`; never print, serialize, or ask an agent to reveal values.
12. **Bound initial cost?** Default to no more than three candidates, five cases, one repetition,
    bounded output, and a pre-run request/cost summary; ask before unknown or expanded spend.
13. **Generated content vs. user input?** Each preset supplies valid structure, two synthetic
    cases, a passing fixture, deterministic validators, conservative execution, and guidance. The
    user or agent must supply representative cases, live candidates, credentials by reference,
    pricing snapshots, task-specific constraints, and any trustworthy semantic rubric.

## Risks and chosen mitigations

- **A runnable sample can look authoritative.** Every generated README and the skill label it a
  plumbing example and require representative replacement data.
- **Broad presets can imply one quality metric.** The document preset chooses one deterministic
  starter shape and explicitly requires task-specific validators for QA, summarization, and
  synthesis.
- **Packaged Markdown/data may be omitted silently.** Archive-member requirements and isolated
  install smoke tests fail the release if any resource is missing.
- **Initialization could destroy work.** Existing destinations always fail; there is no force
  mode, and failure cleanup covers only paths created by the invocation.
- **The package currently has no semantic judge.** Documentation says so and does not disguise
  exact/contains checks as semantic evaluation.
- **Provider/model availability changes.** No live provider or model identifiers appear in
  presets or the skill; provider selection remains a per-run user decision.
